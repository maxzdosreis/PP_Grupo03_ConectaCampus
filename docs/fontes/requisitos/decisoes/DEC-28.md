| **Pergunta** | O Redis, que hoje só conta as tentativas de login, cadastro e troca de senha, pode também guardar a agenda dos espaços e as filas e contagens de reservas, sem tirar do PostgreSQL a garantia de integridade das reservas? Se puder, o que ele guarda, o que acontece quando ele falha ou perde os dados, e o que fica fora? |
| **Resposta do professor** | Não perguntada. |
| **Decisão** | **a) Papéis.** O PostgreSQL é a fonte da verdade das reservas, e a restrição de exclusão `reservas_reserva_sem_sobreposicao_no_espaco` continua sendo a guarda final contra conflito de horário. O Redis guarda só **projeções**, que podem ser reconstruídas a partir do PostgreSQL. O Redis nunca decide conflito, e não há pré-checagem de conflito em script Lua sobre a projeção. **b) Estruturas e chaves** (nomes lógicos). O prefixo é o que o projeto já usa em `contas/api/limites.py`: o `KEY_PREFIX` `conecta-campus` das `CACHES` e a versão padrão do cache do Django, de modo que a chave física é `conecta-campus:1:<nome lógico>`. `agenda:espaco:{id}:{data}` é um Sorted Set com score igual ao início da reserva em minutos; `reservas:pendentes` é um Sorted Set com score igual ao momento da solicitação; `reservas:situacao:{situacao}` é um Set de ids de reserva. **c) Falhas.** A leitura da agenda cai para o PostgreSQL quando a chave não existe ou o Redis falha, e nunca responde 503 por causa disso. A escrita da projeção acontece depois do commit; se falhar, só vai para o log, a reserva fica salva e a projeção se corrige pelo comando de reconstrução ou na próxima leitura. É diferente do limite de tentativas, que continua falhando fechado com 503 ([RNF-F12](../requisitos/rnf.md#rnf-f12) não muda). **d) Persistência.** O Redis padrão continua sem persistência. Um override opcional do Compose com AOF existe só para a demonstração (RDS-09); como a projeção é reconstruível, perder o Redis não perde dado. **e) Escopo essencial:** porta e adaptador da agenda, sincronização depois do commit, leitura com fallback, comando `reconstruir_agenda_redis`, fila de pendentes e contagens, persistência opcional, testes e medição (RDS-03 a RDS-10). **Opcionais:** cache de espaço em Hash com TTL e ranking de espaços (RDS-11 e RDS-12). A resposta da API de ocupação do dia não muda de formato. **f)** A consulta do Gestor à fila e às contagens (RDS-08) é funcionalidade nova: exige um CR e um RF próprios, abertos na própria RDS-08, e fica fora do que esta DEC decide. **g) Fora do escopo:** mover reservas, usuários ou espaços para o Redis como banco primário; pub/sub e filas de mensagens; pré-checagem de conflito no Redis. |
| **Motivo** | O Redis já está no stack e o Trabalho G2 exige uma aplicação prática com modelagem. Ler a agenda por Sorted Set por espaço e dia evita consultar o banco a cada tela e exercita Sets e Sorted Sets, sem trocar a garantia de integridade do PostgreSQL. |
| **Achados** | Nenhum. Surgiu do backlog do Trabalho G2, não do levantamento. |
| **Alternativas** | **i)** Redis como banco primário das reservas, como no esboço do artigo: descartada, porque perde a restrição de exclusão do PostgreSQL e duplica regras de domínio. **j)** Pré-checagem de conflito em Lua sobre a projeção: descartada, porque uma projeção desatualizada geraria falsos conflitos. **k)** Falhar fechado também na agenda: descartada, porque a indisponibilidade do cache não deve impedir a consulta. **l)** Ligar a persistência do Redis padrão: descartada, porque mudaria o RNF-F12 sem necessidade, já que a projeção se reconstrói. **m)** Cache de JSON por `cache.set`: descartada, porque não usa as estruturas do Redis e obriga a desserializar tudo. |
